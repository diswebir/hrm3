# آموزش ساختار و افزودن ماژول

این راهنما برای توسعه‌دهنده PHP نوشته شده است. معماری برنامه از ماژول‌های مستقل PHP استفاده می‌کند؛ فهرست ماژول‌ها هنگام درخواست از پوشه‌ها کشف می‌شود و CRUD معمولی از manifest ساخته می‌شود.

## ۱. ساختار موجود

```text
app/
  bootstrap.php                 ثابت‌ها، نشست امن و ابزارهای عمومی
  Core/
    Database.php                اتصال PDO به SQLite
    Schema.php                  ساخت/ارتقای جداول مرکزی
    ModuleRegistry.php          کشف و اعتبارسنجی manifestها
    RecordService.php           فهرست، اعتبارسنجی، ذخیره و حذف رکوردها
    Access.php                  سیاست نقش‌ها و ماژول‌های حساس
    Audit.php                   ثبت تغییرات مهم
    UploadService.php           بارگذاری خصوصی پیوست‌ها
  Modules/
    employees/module.php        تعریف پرونده کارکنان
    leave/module.php            تعریف درخواست‌های مرخصی
    attendance/module.php       تعریف حضور و غیاب
    ...                         هر ماژول یک پوشه مستقل
  Views/                        قالب‌های رابط مشترک
assets/                         CSS و JavaScript محلی
storage/                        SQLite، تنظیمات و فایل‌های خصوصی
```

ماژول استاندارد رکوردهایش را در جدول مرکزی `records` نگهداری می‌کند (`module`, `title`, `status`, `data`, سازنده و زمان‌ها). ستون `data` یک JSON متنی است؛ بنابراین برای فرم متداول نیازی به ساخت جدول یا تغییر Schema ندارید. فهرست، فیلتر وضعیت، جست‌وجو، صفحه‌بندی، فرم، خروجی CSV و گزارش تغییرات توسط هسته مشترک فراهم است.

## ۲. افزودن ماژول ساده، مرحله‌به‌مرحله

### گام ۱: انتخاب شناسه

یک شناسه انگلیسی کوتاه و یکتا با حروف کوچک انتخاب کنید؛ فقط `a-z`, عدد، خط زیر و خط تیره مجاز است. نمونه: `equipment_requests`.

### گام ۲: ساخت پوشه

```text
app/Modules/equipment_requests/module.php
```

نام پوشه باید دقیقاً با مقدار `slug` یکی باشد. فایل ماژول باید یک آرایه PHP برگرداند.

### گام ۳: تعریف manifest

این مثال یک ماژول «درخواست تجهیزات» است:

```php
<?php
declare(strict_types=1);

return [
    'slug' => 'equipment_requests',
    'name' => 'درخواست تجهیزات',
    'group' => 'عملیات و پشتیبانی',
    'icon' => 'briefcase',
    'order' => 175,
    'description' => 'ثبت درخواست، مسئول پیگیری و وضعیت تحویل تجهیزات.',
    'entity' => 'records',
    'primary' => 'title',
    'columns' => ['employee', 'needed_date', 'priority', 'status'],
    'fields' => [
        [
            'name' => 'title',
            'label' => 'عنوان درخواست',
            'type' => 'text',
            'required' => true,
        ],
        [
            'name' => 'employee',
            'label' => 'درخواست‌کننده',
            'type' => 'employee',
            'required' => true,
        ],
        [
            'name' => 'needed_date',
            'label' => 'تاریخ نیاز',
            'type' => 'date',
        ],
        [
            'name' => 'priority',
            'label' => 'اولویت',
            'type' => 'select',
            'options' => [
                'normal' => 'عادی',
                'urgent' => 'فوری',
            ],
        ],
        [
            'name' => 'status',
            'label' => 'وضعیت',
            'type' => 'select',
            'required' => true,
            'options' => [
                'pending' => 'در انتظار',
                'approved' => 'تأیید شده',
                'delivered' => 'تحویل شده',
                'rejected' => 'رد شده',
            ],
        ],
    ],
];
```

### گام ۴: ورود و آزمون

با نقش مدیر، صفحه را باز کنید:

```text
index.php?page=equipment_requests
```

ماژول باید در منو و صفحه قابل مشاهده باشد. بررسی کنید که ایجاد، ویرایش، حذف، جست‌وجو، فیلتر وضعیت و خروجی CSV درست عمل کند. هنگام نمایش زبان فارسی، املای برچسب‌ها را نیز کنترل کنید.

## ۳. گزینه‌های manifest

| کلید | کاربرد |
|---|---|
| `slug` | شناسه یکتا؛ باید با نام پوشه برابر باشد. |
| `name` | عنوان فارسی ماژول در منو و سربرگ. |
| `group` | گروه منو، مانند «زمان و حضور». |
| `icon` | نام آیکن داخلی مثل `users`, `calendar`, `clock`, `wallet`, `briefcase`, `chart`, `book`, `file`, `building`, `shield`, `spark`, `check`. |
| `order` | ترتیب نمایش ماژول در منو. |
| `description` | توضیح کوتاه بالای فهرست. |
| `entity` | برای CRUD استاندارد از `records` استفاده کنید؛ `employees` مخصوص ماژول پایه کارکنان است. |
| `primary` | نام فیلدی که عنوان ردیف را می‌سازد؛ معمولاً `title`. |
| `columns` | فهرست `name` فیلدهایی که در جدول نشان داده می‌شوند. `status` به‌شکل نشان رنگی نمایش داده می‌شود. |
| `fields` | تعریف فرم و اعتبارسنجی سرور. |
| `sensitive` | اگر `true` باشد، دسترسی مدیر واحد و کارمند مسدود و فقط مدیر/منابع انسانی مجاز است. |
| `employee_read_all` | برای ماژول محتوای عمومی، نمایش رکوردها به کارمندان مجاز را فعال می‌کند؛ فقط در صورت نبود داده حساس استفاده شود. |
| `employee_view` | دسترسی مشاهده کارمند به این ماژول را فعال می‌کند؛ رکوردها به‌صورت پیش‌فرض به سازنده محدود می‌شوند. |
| `employee_manage` | دسترسی سلف‌سرویس کارمند را فعال می‌کند؛ رکوردها به سازنده محدود می‌شوند و حساب باید به پرونده کارمند متصل باشد. برای درخواست‌ها، فیلد `employee` را اضافه کنید تا مالک در سرور به کارمند جاری محدود شود. |

## ۴. انواع فیلد

- `text`: متن کوتاه
- `email`: ایمیل با اعتبارسنجی
- `tel`: شماره تلفن
- `date`: تاریخ میلادی استاندارد `YYYY-MM-DD`
- `month`: ماه `YYYY-MM`
- `time`: ساعت ۲۴ساعته `HH:MM`
- `number`: عدد غیرمنفی
- `select`: انتخاب از آرایه `options` به‌شکل `value => برچسب`
- `textarea`: متن چندخطی
- `file`: PDF، PNG/JPG، DOC/DOCX، XLS/XLSX یا TXT تا ۸ مگابایت؛ فایل در `storage/uploads` می‌ماند.
- `employee`: انتخاب پرونده از فهرست کارکنان فعال

ویژگی‌های متداول فیلد: `name` (الزامی و یکتا)، `label`، `type`، `required`، `placeholder` و `help`. نام فیلد فقط با حرف کوچک انگلیسی شروع شود و از حروف، عدد و `_` استفاده کند. متن‌ها و فهرست گزینه‌ها در manifest قرار دارند؛ مقادیر فرم با prepared statement و اعتبارسنجی سمت سرور ذخیره می‌شوند.

## ۵. نقش‌ها و داده شخصی

نقش‌های مدیر سامانه و منابع انسانی به ماژول‌های مدیریتی دسترسی دارند. مدیر واحد به ماژول‌های غیرحساس دسترسی دارد. کارمند فقط به ماژول‌های مشخص سلف‌سرویس و رکوردهای مرتبط با حساب خودش دسترسی دارد.

برای افزودن دسترسی کارمند به یک ماژول، ابتدا سیاست را در `app/Core/Access.php` بررسی و به allowlist مناسب اضافه کنید؛ برای ایجاد/ویرایش سلف‌سرویس، فیلد `employee` را در manifest بگذارید و منطق مالکیت رکورد را مطابق نیاز محدود کنید. اگر فهرست ماژول برای کارکنان عمومی است، `employee_read_all` فقط وقتی رکوردها واقعاً عمومی‌اند فعال شود. داده‌های حقوق، قرارداد، انضباط، اسناد و خروج نباید عمومی شوند؛ `sensitive => true` را تنظیم و با هر چهار نقش آزمون کنید.

## ۶. چه زمانی جدول اختصاصی بسازیم؟

برای فرم و گردش عمومی، جدول `records` کافی است. اگر ماژول جدید به قیود رابطه‌ای پیچیده، حجم بالای داده، گزارش‌های زمانی دقیق یا محاسبات تراکنشی نیاز دارد:

1. ساختار را به‌صورت migration نسخه‌بندی‌شده در `app/Core/Schema.php` اضافه کنید؛ از اجرای `CREATE TABLE` دستی در هر درخواست خودداری کنید.
2. منطق پایگاه داده را در سرویس مستقل همان دامنه (مثلاً `app/Modules/<slug>/Service.php`) نگه دارید؛ SQL را در view ننویسید.
3. مجوز، اعتبارسنجی، تراکنش SQLite، ثبت Audit و آزمون بازیابی خطا را پیش از افزودن صفحه در نظر بگیرید.
4. مسیر گزارش و خروجی CSV را فقط بعد از بررسی مجوز نقش به کاربر نشان دهید.

این برنامه در نسخه فعلی کشف خودکار برای manifest و CRUD عمومی دارد؛ سرویس‌های اختصاصی نیازمند اتصال کنترل‌شده به هسته‌اند و صرفاً با ساخت فایل Service به‌صورت جادویی اجرا نمی‌شوند.

## ۷. آزمون و انتشار امن

- ابتدا روی کپی آزمایشی و پایگاه داده نمونه توسعه دهید.
- مقدارهای مجاز `select`، تاریخ نامعتبر، عدد منفی، ایمیل غلط، آپلود فایل بزرگ/نامعتبر و توکن CSRF اشتباه را امتحان کنید.
- با مدیر، منابع انسانی، مدیر واحد و کارمند وارد شوید و دسترسی هر صفحه و هر عملیات را جداگانه بررسی کنید.
- خروجی CSV را از نظر متن فارسی، اعداد و داده‌های محرمانه کنترل کنید.
- قبل از انتشار نسخه جدید، از `storage/hrm.sqlite` پشتیبان خارج از public_html بگیرید.
- خطاهای PHP را در محیط عملیاتی به کاربر نمایش ندهید؛ گزارش‌ها را در log خصوصی هاست بررسی کنید.
